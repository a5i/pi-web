# Preview для `.c4` (LikeC4) и `.mdx` в FileViewer

Контекст по итогам исследования: mermaid-интеграция (`components/MermaidBlock.tsx`) — готовый архитектурный образец; `.mdx` уже рендерится как markdown (`EXT_TO_LANGUAGE` в `app/api/files/[...path]/route.ts:50`), но JSX/импорты выводятся сырым текстом; LikeC4 не распознаётся вовсе. У LikeC4 нет SVG-экспорта без браузера, зато есть headless-API: `@likec4/language-services` (npm, есть node-сборка) — `fromSource(src)` → `LikeC4.diagrams()` → `LayoutedView[]` — и официальный React-рендерер `@likec4/diagram` (им рендерят playground и VSCode-webview).

Выбранный подход: **сервер считает вьюхи (langium + graphviz-wasm, оффлайн), браузер лениво грузит рендерер**. MDX — «JSX-tolerant» рендер без выполнения кода.

## 0. Зависимости
- `npm i @likec4/language-services @likec4/diagram` + отдельные micromark/mdast MDX-расширения (`micromark-extension-mdx-jsx`, `micromark-extension-mdx-expression`, `mdast-util-mdx-jsx`, `mdast-util-mdx-expression`, `remark-mdx-frontmatter` не нужен — remark-frontmatter уже есть).
- Версии likec4-пакетов запинить точечно (пакет релизится очень часто).
- Проверить дедупликацию React: `@likec4/diagram` объявляет `react 19.2.8` обычной зависимостью; при расхождении с установленным в pi-web `react ^19.2.4` поднять pi-web до ≥19.2.8 (двойная копия React ломает хуки).
- `next.config.ts` `transpilePackages`: проверить, не тянут ли клиентские чанки likec4 class `static {}` (как mermaid, #753) — при необходимости добавить `@likec4/diagram`, `@xyflow/react` и пр. Регексп-lookbehind в клиентских чанках искать grep'ом: SWC не умеет его транспилировать (риск для Safari 16.2 — см. риски).

## 2. Сервер: вычисление вьюх LikeC4
- Новый маршрут `app/api/likec4/route.ts` — `POST { content }` → `{ views: LayoutedView[], diagnostics }` (один маршрут и для превью файла, и для ```likec4-блоков; GET не годится — контент в теле). Лимит размера контента (напр. 1МБ).
- `lib/likec4-preview.ts`:
  - ленивый `import("@likec4/language-services/node")` (ESM-only — только server-side, никогда не импортировать из клиентских компонентов); `fromSource(content)` → `diagrams()`, ошибки через `getErrors()`;
  - кэш на `globalThis` (переживает HMR, как `__piSessions`) с ключом = хэш контента + single-flight промис (образец — `shareModelCatalogRefresh()`);
  - таймаут-гвард на парсинг/layout.
- v1 — один файл без `include`-директив (покрыть диагностику «include не поддерживается»); `fromWorkspace` с проверкой allow-list — отдельный follow-up, в скоуп не входит.
- Обновление при правке: клиент по существующему `type=watch` SSE переотправляет `POST`.

## 3. Клиент: компонент LikeC4Preview
- `components/LikeC4Preview.tsx` по образцу `MermaidBlock.tsx`:
  - ленивый `await import("@likec4/diagram")` (+ его `styles.css` / `styles-xyflow.css` — импорт CSS из node_modules в ленивом клиентском компоненте; если Next не позволит — импорт на уровне модуля компонента);
  - переключатель вьюх с учётом папок: заголовки вьюх содержат `/` («Deployment / Production») — рендерить сгруппированный список (см. доку, на которую ссылался пользователь);
  - ошибки парсинга → панель диагностики; fallback на вкладку Source уже есть как режим;
  - error boundary вокруг ленивого чанка: при неспособности браузера исполнить чанк (iOS 16.2) — сообщение «откройте вкладку Source», приложение не ломается;
  - при утечке глобальных стилей Mantine — контейнер-скоуп `.likec4-preview-scope` в `app/globals.css`.
- `FileViewer.tsx`: в превью-панели для `isLikeC4` — `<LikeC4Preview>` (тянуть контент уже загруженным `data.content`, POST `/api/likec4`).

## 4. Клиент: MDX-превью (без выполнения кода)
- `lib/markdown-mdx.ts` — remark-плагин `remarkMdxPlaceholders`:
  - парсинг MDX-синтаксиса через micromark/mdast-расширения;
  - `mdxJsxFlowElement`/`mdxJsxTextElement` → элементы с фиксированными тегами (`mdx-flow-component` / `mdx-text-component`, имя и пропсы — в data-атрибутах без экранирования проблем: имя/пропсы сериализовать в `data-props` JSON);
  - `mdxFlowExpression`/`mdxTextExpression` → приглушённый инлайн-токен;
  - `mdxjsEsm` (import/export) → заметка-чип «N import/export — не выполняется». Если ESM-блоки не покрываются отдельно опубликованными расширениями — консервативная построчная предобработка顶层 `import …;` / `export …` до парсинга.
- Рендер плейсхолдеров — компоненты в `components`-маппинге ReactMarkdown (FileViewer-превью): карточка с именем компонента + короткими пропсами, дети рендерятся внутри (WYSIWYG-структура сохраняется).
- Применять только в FileViewer-превью при `getFileExt(filePath) === "mdx"`: `markdownMdxPreviewRemarkPlugins = [...markdownPreviewRemarkPlugins, remarkMdxPlaceholders]` (существующие константы в `lib/markdown.ts:573-590` не менять — чат не трогаем). `rehype-sanitize` пропускает только наши фиксированные теги — расширить `markdownSanitizeSchema` (`lib/markdown.ts:12-23`) точечно.

## Риски
- CSS Mantine/xyflow рядом со стилями pi-web — проверится на первом рендере, митигируется скоупом-контейнером.
- Safari/iOS 16.2: клиентский чанк likec4 может содержать не-транспилируемый синтаксис — error boundary + fallback на Source; основной сайт не затрагивается (всё лениво).
- Обновления likec4 частые — пин версии, обновление отдельным PR.
- wasm-graphviz в Node грузится из node_modules (оффлайн, без CDN) — проверить отсутствие сетевых фетчей при первом рендере.
- Если `@likec4/diagram` не заведётся в Next-клиенте (CSS или MantineProvider) — запасной вариант: `renderToStaticMarkup` на сервере в том же маршруте (возвращает готовый HTML/SVG), но это запасной, не план А.
